# Обучение snn-lm: корпус, сборка, запуск, возобновление

Пошаговая инструкция: от пустой машины до обученной и экспортированной модели.
Полный справочник флагов — в [lm/README.md](../lm/README.md#флаги).

## 1. Требования

- Rust (stable, 1.89+), Linux x86-64. Обучение идёт на CPU: 4 ядра и 16 ГБ RAM
  достаточно (пик ~5–6 ГБ при `--micro 3`).
- ~6 ГБ диска: корпус 1.3 ГБ parquet, токены 0.85 ГБ, сборка ~3.5 ГБ, прогон
  ~35 МБ плюс состояние возобновления (см. ниже).

## 2. Корпус

Корпус не хранится в git. Скрипт `lm/data/fetch.sh` скачивает 5 шардов
Taiga proza (проза с proza.ru, `cointegrated/taiga_stripped_proza`,
CC BY-SA 3.0, ~2.4 ГБ текста), проверяет их SHA-256 и кладёт в каталог,
где их ищет `prepare`:

```bash
lm/data/fetch.sh                      # в /home/user/data/taiga
lm/data/fetch.sh /mnt/corpus/taiga    # или в свой каталог
```

Уже скачанные файлы повторно не качаются, но проверяются. Свои тексты
(UTF-8 `.txt`, например собственные книги) положите в `<каталог>/extra/` —
каждый файл станет отдельным документом. Тексты под авторским правом в
репозиторий не коммитятся.

Затем токенизация:

```bash
cargo run --release -p snn-lm -- prepare \
    --src /home/user/data/taiga --out /home/user/data/prepared \
    --vocab 6561 --sample-mb 64
```

`prepare` читает все `*.parquet` и `extra/*`, обучает BPE на выборке
(`--sample-mb` МБ, каждый 7-й документ), кодирует корпус и пишет в `--out`:

| Файл | Что это |
|---|---|
| `tokenizer.bpe` | BPE на 6561 = 3⁸ токенов (байты, `<doc>`, слияния) |
| `train.bin` | токены обучения (u16, документы через `<doc>`) |
| `val.bin` | валидация — каждый сотый документ |

Словарь 6561 менять нельзя без переобучения модели: он задаёт эмбеддинг.

## 3. Сборка

```bash
cargo build --release -p snn-lm                   # переносимая: target/release/snn-lm
scripts/build-native.sh                           # под этот CPU: target/native/release/snn-lm
scripts/build-native.sh --features vnni           # + VNNI-ядро движка (инференс)
cargo build --release -p snn-lm --features vnni   # VNNI без target-cpu=native
```

- **Native** (`-C target-cpu=native`) включает все расширения процессора
  (на Xeon с AVX-512 обучение быстрее на ~8%). Бинарник запускается только на
  таких же CPU, поэтому собирается в отдельный `target/native`.
- **`--features vnni`** — целочисленное ядро тернарных матриц движка
  инференса (`chat`, `probe`, `copyeval`) на AVX-512 VNNI (`vpdpwssd`):
  веса хранятся как int16, активация раскладывается на старшую часть int16
  и остаток int16 (~30 бит, ошибка ≤10⁻⁶), скалярные произведения — в i32.
  Матрицы движка считаются в 7–21 раз быстрее
  (`cargo run --release -p snn-lm --features vnni --example kernels`). Наличие VNNI проверяется во
  время работы, на других CPU используется обычное ядро «сдвиг-сложение».
  На обучение фича не влияет.

Для долгого прогона копируйте бинарник рядом с данными, чтобы пересборка
не подменила его на ходу:

```bash
cp target/native/release/snn-lm /home/user/data/snn-lm.run
```

## 4. Запуск обучения

Рекомендуемый короткий прогон (3 часа, косинус lr по времени до 0.4·lr):

```bash
nohup /home/user/data/snn-lm.run train \
    --data /home/user/data/prepared --out /home/user/data/v4a \
    --hours 3 --lr 2e-3 --warmup 243 --seed 29 \
    --log-every 27 --val-every 243 --micro 3 --state-trits 2 \
    > /home/user/data/v4a/stdout.txt 2>&1 &
```

- `--hours H` — расписание lr по прошедшему времени, остановка через H часов.
  Без него расписание идёт по `--steps`.
- Размер модели задают `--layers`, `--mlp`, `--state-trits`; они
  записываются в `model.cfg` прогона, и все остальные команды читают их оттуда.
- `--micro` — потоков в группе при накоплении градиента: пик памяти
  пропорционален группе (27 потоков при `--micro 9` — ~10 ГБ, при `--micro 3` — ~5 ГБ).
- `--init путь/model.safetensors` — тёплый старт из чужого чекпоинта
  (тензоры, которых там нет, остаются со своей инициализацией).

### Что пишется в каталог прогона

| Файл | Содержимое |
|---|---|
| `model.cfg` | размер модели (`layers`, `mlp`, `state_trits`) |
| `model.safetensors`, `model.ema.safetensors` | последние веса и их EMA (каждые 81 шаг) |
| `step` | номер последнего сохранённого шага |
| `log.tsv` | step, loss, plain, fact, reread, template, known, ток/с, lr, времена fwd/bwd/opt/ckpt |
| `val.tsv` | step, val-loss весов, val-loss EMA (каждые `--val-every` шагов и в конце) |
| `snapshots/stepN*.safetensors` | веса и EMA на каждом замере валидации |
| `resume/` | полное состояние для точного возобновления |
| `stdout.txt` | всё, что печатает `train`, включая `head:`, `steps:`, `quant:` |

Колонки `log.tsv`: plain — обычный текст, fact — ответы на вопросы о фактах
(должны копироваться из памяти), reread — повторное чтение,
template — «не знаю / мой друг», known — доля блоков, где SNN-память уверена.

## 5. Остановка и возобновление без потерь

Каждые 81 шаг (и на последнем шаге) `train` пишет в `resume/` всё, что нужно,
чтобы продолжить так, будто остановки не было:

- веса, EMA, моменты AdamW трёх оптимизаторов и их счётчики;
- прошедшее время расписания `--hours` (косинус продолжается с того же места);
- рекуррентные состояния, K/V предыдущего окна и позиции всех потоков;
- SNN-память каждого потока целиком (лексический и семантический индекс,
  K/V, токены) и индекс индукции.

Потоки данных детерминированы по `--seed` и при возобновлении
перематываются до того же места, поэтому данные не повторяются и не
пропускаются. Состояние сначала пишется в `resume.tmp/` и только потом
подменяет `resume/`, так что сбой во время записи не портит прошлое.

Остановить без потерь: `kill -TERM <pid>` (или Ctrl+C). Процесс дописывает
текущий шаг, сохраняет `resume/` и выходит. Продолжить — **той же командой**
с тем же `--out` (и теми же флагами): `train` найдёт `resume/state.txt` и
напишет `resumed exactly from step N`. После `kill -9` или падения теряются
только шаги после последнего сохранения (не более 81).

### Продолжение с чекпоинта в репозитории

Точное состояние (`resume/`, ~1 ГБ) в git не хранится. В репозитории лежат веса последнего
прогона: `lm/checkpoints/v4c/model.safetensors` и `model.ema.safetensors` (+ `model.cfg`).
Новый прогон с них — тёплый старт: моменты оптимизатора и память потоков начинаются заново.

```bash
snn-lm train --out /home/user/data/v4d --init lm/checkpoints/v4c/model.ema.safetensors \
    --hours 3 --lr 2e-3 --warmup 54 --seed 29 --log-every 27 --val-every 243 \
    --micro 3 --parallel 5 --state-trits 2
```

## 6. Оценка, экспорт, чат

```bash
R=/home/user/data/v4a
snn-lm eval     --run $R [--weights ema]      # val-loss с памятью и без
snn-lm recall   --run $R --episodes secret    # вспоминание фактов на 243 … 300 000 токенов
snn-lm reread   --run $R --file книга.txt     # точность повторного чтения
snn-lm ablate   --run $R                      # вклад состояния и позиции в окне
snn-lm export   --run $R [--weights ema] --out lm/model
snn-lm chat     --model lm/model              # диалог: реплики «- …»
snn-lm copyeval --model lm/model              # точное копирование из памяти движком
```

`--weights ema` берёт усреднённые веса вместо последних. Перед сравнением
моделей смотрите `val.tsv`: EMA обычно лучше последних весов в конце прогона.
